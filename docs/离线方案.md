# 离线访问方案（App v0.18 → v0.19）

> 需求（用户原话，2026-10-14）：「目前这个项目做了本地缓存来实现更快加载，但是当主机离线时或客户端离线时手机上会出现无法连接，现在需要实现的是在主机或客户端离线无法连接时，手机上也能离线访问页面功能」
>
> 结论：**自研**（档 1 + 档 2/B1）。v0.18 实现并发布；用户看过成品后改了呈现方式，**v0.19 修订见 §7**（离线看到的就是页面本身，不再是另一个页面）。

---

## 1. 需求锁定

| | |
|---|---|
| 输入 | 手机上的 DSH App（WebView 壳），通过隧道连电脑上的桥接 |
| 输出 | 电脑关机 / 桥接没跑 / 手机完全没网时，App 打开仍是一页可读的内容，而不是「无法连接」 |
| 谁用 | 只有手机主人自己；只读，不写 |
| 硬约束 | 不引入新依赖（`build.gradle.kts` 只有 `androidx.core:core:1.13.1`）；Java 17；`minSdk 26`；保持现有 origin（`localhost:17800`）不换，否则 cookie/session 掉线；离线数据必须能被用户一眼认出是旧的 |

**「离线」的两个成因**（这是本方案的全部出发点）：

1. **电脑不可达**（关机、桥接没跑、不在同一网络）→ `WebActivity.connect()` 在 `Upstream.probe` 失败时直接弹「无法连接」覆盖层，**页面根本没加载**。
2. **手机没有网络** → 隧道建得起来，但上游连不上，同样是覆盖层。

无论哪一种，DSH 前端本身也救不了：它的数据全走一条 WebSocket（`/api/remote.mux`），断线后 SPA 只会进入「断线/重连」状态，不会用缓存渲染会话。

## 2. 先找再造：候选项目调研

按 reuse-first 规则先搜现成方案，结论如下（关键数字均有来源链接）。

### 1. **Workbox** — https://web.dev/articles/offline-fallback-page
- 维护：活跃（Google 官方）· 许可证 MIT
- 部署：Service Worker，纯前端
- 可复用：`workbox-precaching` 预缓存 + `setCatchHandler` 离线兜底页
- 要改：**只能解决「资源」，解决不了「数据」**。`/api/remote.mux` 是一条 WebSocket，Workbox 管不到；而且 Service Worker 的 fetch 会绕过 `shouldInterceptRequest`，与现有 `AssetCache` 形成两层缓存，行为难推理
- 判定：**只配当补充，不能当方案**

### 2. **HLLOfflineWebView-android** — https://github.com/HuolalaTech/HLLOfflineWebView-android
- 维护：**停滞**，最后提交 2022-07，全仓库只有 2 个 commit、0 个 tag，275 star
- 部署：Apache-2.0，但模型是「服务端下发 H5 离线 zip 包」，且**必须自建 `queryOffline` 接口**
- 可复用：离线包拦截的思路
- 要改：它的前提是「服务端活着」，与「PC 主机挂了手机还能看」正好相反；而且和已有 `AssetCache` 功能重叠
- 判定：**不推荐**

### 3. **AndroidX WebKit** — https://github.com/tauri-apps/wry/issues/1709
- `WebViewAssetLoader` 会**换掉 origin**，本项目 cookie/session 绑在当前 origin 上，用了就掉登录
- 但 `ServiceWorkerController` 本身可用：`http://localhost` 是 secure context（决策 17 用 `localhost` 不用 `127.0.0.1`，刚好满足前提）
- 判定：**不使用**（换 origin 的代价不可接受）

### 结论：**没有能直接用的对口项目，自研**

理由：需求的核心是「**PC 不在了**还要能看**会话内容**」，而现成项目全都在解决「**服务器在**、只是网络抖」的资源缓存问题。数据这一半没有任何开源项目替我们做。

## 3. 实现

三个档次，最终做的是**档 1 + 档 2（快照来源选 B1）**。

| 档 | 内容 | 是否做 |
|---|---|---|
| 档 1 | 根文档 `/` 可缓存 + 主机不可达时不再回 502，改回放本地页面 | ✅ |
| 档 2 | 在线时抓一份只读快照存手机，离线时渲染它 | ✅ |
| 档 3 | 在 Tunnel 里录制 `/api/remote.mux` 的 WebSocket 帧并离线回放，让真 SPA 离线渲染 | ❌ 工作量大、脆弱、收益低 |

档 2 的快照来源有两个子选项，选 **B1**：

- **B1（选它）**：桥接端新增 `/__bridge/offline/snapshot.json`，直接读 DSH 自己的会话日志生成。**不需要 DSH GUI 参与，也不需要 `/api`**
- B2（弃）：App 注入 JS 抓渲染后的 DOM。依赖前端实现细节，前端一改就崩

### 3.1 数据流

```
在线（不变）：
  手机 App ──隧道 17800──> 桥接 3080 ──> DSH 19387
                └─ 页面加载完成 / 回到前台时，额外拉一次
                   GET /__bridge/offline/snapshot.json  → 写进 App 私有目录

离线（新增）：
  手机 App ──隧道 17800──> 上游 TCP 连不上
                └─ Tunnel 认出「这是一次页面导航」→ 200 text/html
                   Offline.page()：assets/offline.html + 内联的本地快照
```

### 3.2 桥接：`tools/dsh-lan-bridge.cjs`

新增路由 `GET /__bridge/offline/snapshot.json`（要过原来的 gate cookie）。

数据源是 DSH 自己写的会话日志：`%DSH_HOME%\sessions\<slug>\<session>\session.v4.jsonl.zstd`。**一个日志文件是「每轮一个 zstd 帧」**，所以必须逐帧扫（`zstdDecompressSync` 只解第一帧），和 `tools/session-text.cjs` 用的是同一套办法。

| 常量 | 值 | 含义 |
|---|---|---|
| `SNAPSHOT_TTL_MS` | 60 s | 手机每次开屏都来问，日志解压是 30 MB 级的活，缓存一分钟 |
| `SNAPSHOT_LIST` | 40 | 列表最多 40 个会话 |
| `SNAPSHOT_BODIES` | 12 | 其中最新 12 个带正文 |
| `SNAPSHOT_MESSAGES` | 40 | 每个会话最多留最近 40 条消息 |
| `SNAPSHOT_TEXT` | 4000 | 单条消息最多 4000 字符 |
| `SNAPSHOT_MAX_BYTES` | 2 MB | 超了就从最旧的开始丢正文，列表永远保留 |

只取「人能读的」：`user/message` 里 `source.kind === "user"` 的才算真人输入（同一类型还承载注入的 runtime context、skill 目录、审批答复）；`assistant/message` 只取 `content[].type === "text"`，推理和工具调用丢掉；同一个回答的多个 step 记录会合并成一条。

### 3.3 App：`Offline.java`（新增）

- 存放位置：`filesDir/offline/snapshot.json` —— **不是 cache 目录**。「清除缓存」不能把唯一的会话副本一起清掉
- `sync(Context, tunnelPort, key)`：**走 App 自己的隧道**去拉，而不是直连上游。隧道已经指向当前选中的地址，而且 PC 不在时它的兜底会对这个路径回 503，正好当「没得同步」的信号。先写 `.part` 再 rename，失败不会毁掉旧副本；>4 MB 的一律不认
- `page(Context, reason)`：读 `assets/offline.html`，把快照**内联**进去 —— 一个请求就是整页，后面没有任何东西还能失败
- `render(...)` 单独拆出来，是为了让 PC 上的 JVM 测试能直接驱动它：这里是「任意会话标题」撞上 `<script>` 块的地方，也是最值得钉死的地方

### 3.4 App：`Tunnel.java`

原来上游连不上就直接回 502 HTML。现在：

- **只读 request line**，不解析别的。这是它唯一多看的一点东西
- 只有 `GET /`（可带 `?k=`，或 `/index.html`）算「页面导航」，才交给 fallback
- **其他一律 `503 text/plain`**：`/api`、SSE、轮询的 `/dsh-whale/*.json`、桥接注入的脚本 —— 一个 fetch 拿到 200 和一段 HTML 不会报错，它会报「乱码」，所以宁可让它照常失败
- 没有装 fallback 的隧道（比如单测里的）行为不变，还是 502

### 3.5 App：`assets/offline.html`（新增）

配色直接抄 `res/values/colors.xml` 和它的 night 版本，所以它和 App 其他部分是同一个表面，而不是「浏览器错误页刷了层漆」。

- 顶部：`连不上电脑` / `离线可读`、上次同步时间 + 「N 分钟前」、`N 个会话，其中 M 个有正文`、失败原因（小字）
- 列表：标题、目录名、更新时间、`有正文` 标记
- 点进去：只读对话气泡，用户靠右、助手靠左
- 没有快照时：「没有本地缓存」+ 一句怎么才能有
- 按钮：`重试连接`（走 `AndroidBridge.offlineRetry()`，让 App 重新选地址再加载，不是页面自己 reload）、`回到列表`
- 底部：「内容为上次在线时的快照，仅供离线查看；电脑恢复后点「重试连接」」

### 3.6 App：`WebActivity.java`

| 位置 | 变化 |
|---|---|
| 常量 | `SYNC_EVERY_MS = 10 min`、`SYNC_DELAY_MS = 3000`、`OFFLINE_RETRY_MS = 20000` |
| `offline` 标志 | 屏幕上是不是那张本地页 |
| `connect()` | probe 失败**不再弹覆盖层**，照常 `loadUrl`：隧道会用本地页回答。已经在离线页上时**不重载**（重载会把用户读到的位置滚没了），只把状态栏改回「离线」 |
| `probeAgainTask` | 离线期间每 20 s 问一次「电脑回来了吗」，**只有真通了才 `open()`** |
| `retryFromPage()` | 离线页的「重试连接」按钮 |
| `renewUpstream()` | 判定条件加上 `offline`：从后台回来时，电脑可能已经好了 |
| `syncSnapshot()` | 页面加载完成 + 每次回前台（10 分钟限流）各拉一次快照 |
| `strings.xml` | 新增 `st_offline` = 「离线」 |

## 6. 边界与已知风险

- **快照是「上次在线时」的**，页面上有醒目标注；不保证最新
- 只有最新 12 个会话有正文，其余只有标题；单条消息超 4000 字符会截断并加 `…`
- 整个快照 ≤ 2 MB（桥接端裁剪）、≤ 4 MB（App 端才收）
- `session.v4.jsonl.zstd` 是 DSH 的内部格式，**DSH 大版本升级若改了日志结构，桥接端要跟着改**；但日志本来就在磁盘上，不依赖任何 API 承诺
- 离线页与在线页面是两个不同文档，**离线时看不到 DSH 的界面**（这是档 3 才解决的事）—— **v0.19 已推翻这一条，见 §7**
- 清「应用数据」（不是清缓存）会连快照一起清掉

## 7. v0.19 修订：离线看到的就是页面本身

用户看过 v0.18 的成品后改了要求（原话）：「离线界面要与正常页面一样，不是单独一个页面，而是保持不变，只是在顶部显示ip那里显示未连接即可」。

于是呈现方式整个换掉。**档 2 抓的那份快照仍然照抓，但不再用来渲染离线主界面**：

| | v0.18 | v0.19 |
| --- | --- | --- |
| 离线主界面 | App 自绘的 `assets\offline.html` + 会话快照 | **在线时缓存下来的整份首页 HTML**，原样回放（`Offline.shell()` → `filesDir\offline\shell.html`） |
| 顶栏状态 | 「离线」 | 「未连接」（`st_offline`） |
| 快照的用途 | 就是离线界面 | 降级成**兜底页**：只有手机从没缓存过壳页面时才看得到 |
| 新路由 | 无 | `Tunnel.OFFLINE_ROUTE = "/__offline"`，本地作答、**不拨上游** |
| 上游探针 | 裸 TCP `connect()` | 发 `GET /__bridge/lan.json HTTP/1.0` 并等 HTTP 状态行 |

改动落在四处：

1. `Offline.java` —— `sync()` 里除快照外再抓一份首页 HTML 存 `filesDir\offline\shell.html`；新增 `shell()`（`File`）与 `shellBody()`（字符串）；两次抓取抽成共用的 `get()`；`MAX_SHELL_BYTES` 单独限制壳页面大小。
2. `WebActivity.java` —— `Client.shouldInterceptRequest` 在 `offline && isDocumentPath(path)` 时直接回 `shellBody()`（**这是离线主路径**）；`onReceivedError` 收到主帧错误也改加载 `offlineUrl`；`setOfflineStatus()` 统一顶栏文案；`offlineFallback()` 优先回壳页面、没有才回自绘兜底页。
3. `Tunnel.java` —— 新增本地路由 `/__offline`，在 `up.connect()` **之前**处理；配 `target(head)` / `isDocument(head)` / `offlineReason(head)` 三个纯函数（`offlineReason` 从 `?why=` 取回失败原因，让兜底页能显示「为什么连不上」）。
4. `Upstream.java` —— `probe()` 改成 HTTP 级探测（见下）。

### 为什么非加 `/__offline` 不可

真机验收踩到一个真实缺陷：**PC 的 `frpc.exe` 掉了、云上 `frps` 还在**时，`47.76.59.5:8443` 仍然接受 TCP 连接，然后把连接立刻丢掉。于是：

- `Upstream.probe` 的裸 TCP `connect()` 返回成功 ⇒ App 判定「电脑在」⇒ `offline = false` ⇒ 隧道照常转发 ⇒ WebView 拿到空响应 `net::ERR_EMPTY_RESPONSE` ⇒ `onReceivedError` 弹出**「无法连接」说明板**，而不是离线界面；
- `Tunnel.answer()` 那条兜底**根本没机会跑** —— 它只在 `up.connect()` 抛异常时才走，而这里 connect 成功了；
- `failed = true` 让 `renewUpstream()` 每约 2 s 重来一次，表现为重载循环。

两条修法：

- `Upstream.probe()` 从裸 `s.connect(...)` 改成**发一个 `GET /__bridge/lan.json HTTP/1.0` 并等状态行**，只认 `HTTP/` 前缀（桥接门禁回 401 一样证明桥接在跑）。判定口径变成「**TCP 连上 ≠ 对面有东西**」。
- `Tunnel` 增加本地路由 `GET /__offline`，不拨上游直接回 200；`offlineFallback().page()` 里再补一刀 `offline = true`（该字段因此改成 `volatile`），因为「已经走到兜底」比任何探针都可信。

### v0.19 的验收（真机：小米 2509FPN0BC / API 37，无线 adb，2026-10-14）

| 步骤 | 结果 |
| --- | --- |
| 联网打开一次 | logcat `offline snapshot refreshed`；`filesDir\offline\` 下 `shell.html` + `snapshot.json` 都在 |
| `tools\bridge-off.cmd` 停桥接 → 重启 App | 顶栏 **未连接**，页面**仍是 DSH 自己的界面**（左 rail / 鲸鱼 / 输入框都在），无覆盖层、无 `ERR_EMPTY_RESPONSE`、logcat 无 `load failed` |

### v0.19 之后仍然存在的边界

- 离线时 `/api` 与 `remote.mux` 都拿不到数据 ⇒ **页面打开了，但会话内容是空的**。这是 v1 的既定边界；要填上就是档 3（录制并回放 mux 帧）。
- 只有「手机从没缓存过壳页面」时才会退到 `assets\offline.html` 那张兜底页 —— 也只有在那一页上，才有「最近 40 个会话 / 最新 12 个带正文」的能力。
